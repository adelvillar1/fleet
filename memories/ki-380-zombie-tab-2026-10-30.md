The beta shakeout's second real-use find and the session's "major
regression", filed and pushed (2361023). **The full chain**: the
owner's "warmup" run (Ask-before mode) stood an approval seat for
`tool_search` — a read-only search; the seat's cue lived on the
owner's page; my relaunch (answering the first stuck report) killed
the server the tab was talking to; the tab became a ZOMBIE — the
warmup fetches fail into `.catch(function () { })` (readHome,
readSessions, readMemory, readSkills all swallow), the `/events` SSE
dies, nothing re-arms — and the seat re-stood on the resumed session
where no living page could show it. The run hung behind a seat the
owner could not see or answer for hours. The server was healthy
throughout (every endpoint 200 in milliseconds; a fresh Playwright
page painted whole in 1.5 s — the owner's TAB was the casualty).

**The unstick** (the ops facts worth keeping): read the seat from
`/api/state`'s `approval` field; answer with
`POST /api/approve?session=<seat's session>` and the body
`{"decision": "..."}` — the vocabulary is **always / yes / deny**
(`approve` is refused: "not a decision this seat answers"). `always`
cleared the seat, the tools ran, the run completed. Follow-up named in
the row: the reply's `rule: null` — the standing-rule write did NOT
land, so the next `tool_search` may ask again.

**The open remedy** (KI-380's fix, not yet built): the reads' failure
path re-arms with a bounded retry instead of silent catches; a visible
"the connection was lost — reload" banner replaces the frozen waiting
card; the seat's cue escapes the tab (tab title / notification); the
standing-rule write verified. The general lesson: **a relaunch under
the owner's open tab creates the very hang being reported** — diagnose
(`/api/state`, a fresh Playwright page as the control) before
restarting, and tell the owner to reload the page as part of the fix.
