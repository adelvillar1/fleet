The owner's 2026-10-16 "reset to default" scare: zcode desktop (3.15.3) showed default-only providers. Root cause (host log, `~/.zcode/v2/logs/`): `[provider-config] Personal Provider Config 加载失败…以内存空配置降级` — a ZodError on `manualProviderModelRules[2].config.optionSpecs` (undefined). The step-5-preview rule added during the stepfun-vision session (2026-10-16 00:04) lacked `optionSpecs`, which the app's schema requires on every `modelConfigRules.manualProviderModelRules[]` entry; one invalid rule rejects the WHOLE file and the UI falls back to empty. The disk file is preserved, not rewritten.

**Second occurrence, same day (~18:17):** the owner asked a zcode session to "fix the token window limits on all the models"; it rewrote provider_config.json at 17:33 (`bak-20261016-contextfix`), setting `maxOutputTokens` on every rule but dropping `optionSpecs.reasoningLevel` from 29 rules and `optionSpecs` entirely from 15 — 44 of 48 rules invalid, whole file rejected again. The systemic lesson: **any session that edits provider rules can take down the whole provider list**, because the schema is all-or-nothing; a partial write is a total outage. `setting.json` survived both times unchanged (it holds only selections — verify against `~/.local/share/agent-config-backups/<day>/zcode-v2__setting.json` before assuming a reset).

**Third occurrence (2026-10-17 ~20:14), repaired 20:47 — a NEW failure variant:** adding an `ollama-cloud` provider + a `gemma4:31b` rule tripped not a *missing* field but an **unrecognized key**: `unrecognized_keys: ["supportsImage"]` at `manualProviderModelRules[48].config.properties` (Zod strict on `properties`; the schema-conformant home is `properties.inputFormat.supportsImage`, which the rule already had — the edit had duplicated the flag one level up). Same diagnosis (the host log names the exact path — grep `Personal Provider Config` in the newest `~/.zcode/v2/logs/*.log`), same scripted repair + live pickup (last failure line 20:46:38, repair written 20:47:35, all later polls silent; owner confirmed the provider list restored). Two secondary defects found in the same new rule and fixed with it: its `providerId` was `stepfun` (template leftover — the ollama-cloud provider's own `modelOrder`/`personalModelIds` name `gemma4:31b`), and its `maxOutputTokens` (168000) exceeded its own `contextWindow` (131072) — both template-copied from a stepfun sibling; the window/output pair was LEFT as-is and flagged, not invented. **Validation success ≠ functional**: the `access.apiKey` was the literal placeholder `PASTE-YOUR-OLLAMA-KEY-HERE`, which is a valid string — Zod never complained about a provider that would 401 on every call. The owner's real key was pasted in afterward and also sourced into `~/.fleet/.env` as `OLLAMA_API_KEY` (recorded in [[fleet-vision-gemma4-default]]). Structural facts: the file nests under `config.modelConfigRules.manualProviderModelRules` (49 rules now); backups follow `.bak-<purpose>-<stamp>` beside the file.

**Recovery pattern:** the definitions live in `~/.zcode/v2/provider_config.json` (with the owner's `.bak-*` backup chain); `~/.zcode/v2/setting.json` holds only selections; kit-side copies at `~/.zcode/router/` and a third key copy at `~/.fleet/.env`. Diagnosis: grep the newest `~/.zcode/v2/logs/*.log` for `Personal Provider Config` — the ZodError names the exact failing indices and field paths. Repair (script, not hand): back up beside the file as `.bak-repair-<stamp>`, then per failing rule add `optionSpecs.reasoningLevel` mirrored verbatim from any healthy rule (values `["disabled","enabled"]` + the standard map), and where `optionSpecs` is absent entirely add `maxOutputTokens` reused from a sibling rule of the same provider (every provider's own max was already on disk both times — invent none). Then have the owner reload — no restart needed (owner-confirmed 2026-10-16: the desktop picked up the repaired file live, providers restored without quitting). Never edit provider settings while degraded (an in-memory write can clobber the disk file). Related: [[wip-provenance-stamp-idea]], [[agent-config-backup-hardening]], [[fleet-compaction-budget-is-window-aware]].

**Verified end state (same session):** the 17:33 write was the owner-requested token-window fix and it landed correctly — the repair preserved every value it wrote. `step-5-preview`'s `properties.contextWindow` traced 128000 (`bak-repair-2026-10-16-1530`) → 1000000 (`bak-20261016-contextfix`) → 1024000 (post-repair), all 44 added rules carry a window, none is under 64K, and each provider's `maxOutputTokens` came from a sibling rule already on disk. The two token fields are different things and easy to confuse: the window is `config.properties.contextWindow`, the output cap is `config.optionSpecs.maxOutputTokens.max`.

**Smoke-test timing (2026-10-18):** a cold `fleet gui --port 0 --no-open` prints its URL line LATER than 2 seconds on this machine (binary + the 441-skill scan), so a fixed `sleep 2` before grepping the log reads an empty URL and curls nothing. Wait on the URL in a loop (up to ~10s) instead.
