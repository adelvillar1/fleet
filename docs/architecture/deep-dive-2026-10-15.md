## What fleet is today

One static Rust binary, no Node, no checkout dependency: a native
DeepSeek-API-lineage agent whose everyday surface is a ratatui TUI
(bare `fleet`), with 22 headless subcommands over the same cores. A run
is routed across an eight-provider roster by a sys1 judgment with
failover, steered by a git-tracked markdown fact corpus through a
six-channel ranker, delegated to depth-2 subagents on the parent's own
route, and audited end-to-end: every model-visible thing is
reconstructable from an append-only JSONL session log, and every
decision lands a row in the dev-decisions calibration stream.

## The run path

```
fleet run "<task>"  (or the TUI, or a cron fire)
  └─ main.rs dispatch → credential resolution (env → <FLEET_HOME>/.env,
     and nothing else — the 2026-10-16 ruling removed the harness leg)
  └─ route::select: pin wins → else sys1_classify judges the workload
     (cached per task, keyed to the judging lane) → the workload's
     preference list is the walk → gates (confidence < 0.6 ⇒ the
     default workload as a Fallback, never claimed as a judgment)
  └─ agent loop (agent.rs run_task):
       per turn: read the owner's control file (steer/stop) → assemble
       the memory block once at run start (protected tier → primary
       pool → spillover by three named routes → working memory, all
       inside a 2048-token budget) → stream the request with the
       dynamic declarations (built-ins + skills + lanes joined so far)
       → tool calls: approval gate one call at a time → execute (waves,
       writers serial) → log every message as it happens → between
       turns: the window check, one compaction per crossing
  └─ exit: end record (completed / max-turns), one turn row in the
     calib stream, every spawned lane child closed on every path
```

## Routing: the chain, and where DeepSeek sits

The declared chain (the owner's standing directive, `route.rs:143-260`):
zai-coding-plan → xiaomi-mimo → stepfun → token-plan →
**deepseek** → liquid (declared after DeepSeek, outside the chain until
the owner's config moves it) → blend1 (lane-kind, the composed
workload's grounding candidate). DeepSeek is the only `Billing::Payg`
entry — the working account held in reserve, declared in no workload's
chain, so it serves only when the owner pins it. The precursor's
`router-kit` entry that once headed this chain was removed 2026-10-16.

Three facts pin the reserve semantics exactly:

1. **No workload's preference list names deepseek** — the kit's
   `allowPayg: false` ported as policy (`route.rs:276-334`), so the
   judged path never selects it.
2. **A pin selects it** — a provider pin routes every shape through
   that provider's own models (`route.rs:960-1039`). The machine's
   current pin is stepfun.
3. **The empty-table path walks the whole declared chain** — a decision
   that carries no order walks every resolved candidate in chain order
   with each one's default model (`route.rs:1490-1496`). That is the
   last-resort path the owner named: with the five plan candidates
   failing with failover-eligible classes — a 402 maps to `quota`
   (`route.rs:1299`), a dead endpoint to `network` — the walk advances
   down the chain and DeepSeek answers when no other viable provider
   remains. Liquid sits after it and is unusable without its key;
   blend1 is lane-kind and serves only the `composed` workload.

Around the walk: the calibration ride-back can skip a mid-walk
candidate whose (provider × workload) cell is fit and wrong at ≥ 0.50 —
never the start, never the last healthy candidate (`route.rs:1549-1578`);
a demotion streak of three failed attempts moves a candidate to the end
of the session's walk (`calib.rs:1581-1601`, `route.rs:2038-2054`); a
mid-stream failure is fatal rather than a failover; an exhausted
preference list fails the run by name rather than falling through to a
candidate no workload asked for.

## The recall core

Six named channels, one weighted sum, no shape term — the shape
partitions the pool upstream (`memory.rs:2319-2435`):

| Channel | Weight | Measures |
|---|---|---|
| trajectory | 0.30 | the fact's recorded phrases against the instruction's trajectory — the largest channel, the owner's "key information" |
| history | 0.25 | recall-count earned by use, capped at 8 |
| vector | 0.15 | cosine, instruction ↔ the fact's indexed text |
| keyword | 0.15 | how much of the instruction the topic text answers |
| freshness | 0.10 | exponential decay, 90-day half-life |
| provenance | 0.05 | `confirmed-by` 1.0 vs `inferred` 0.5 |

The slice-19 reweighting is the design ruling in constants: the topical
pair sums to 0.30 ("the neighborhood") against 0.60 for the direction
channels, so maximum proximity with no direction evidence cannot
outrank a fact pointing at the minima. Entry needs `MIN_RECALL_SCORE`
0.20; the shape's own pool stands alone only at `SPILLOVER_FLOOR` 0.50,
below which the strongest off-shape fact enters marked `off-shape`
through one of three named routes. The protected tier (`user` /
`feedback` facts) never competes and is never evicted, even past
budget.

The substrate is one markdown file per fact under `memories/` at the
repo root (home-first, then ancestor-walked from cwd (`resolve_root_from`, KI-087)), git-tracked,
with the recall-count bump as the only in-place rewrite — one frontmatter
line, through one rewriter, temp-plus-rename. Recall hits fire at
assembly time, before the model call: the known timing gap is KI-068 —
the numbers describe recall attempts, not recalls the model saw.

The session archive rides the same ranker unchanged: one synthetic fact
per log whose phrases are the session's successful tool calls, whose
shape is its outcome word (`completed` → `resolved`, `max-turns` →
`incomplete`, else `diverged`), whose basis is `inferred`, cached in a
second embedder-keyed index under the sessions directory
(`session_recall.rs:144-163`). Its own feedback loop is the one deferred
leg of the archive plan — a synthetic fact's path is the session log,
so the corpus's bump must never be pointed at it.

## Delegation, scheduling, and the beats

A child is the same `Agent` over an ordinary session on the parent's
own routed client — "never downgrades" is structural, not a rule
(`subagents.rs`). Depth is capped at 2 (`SUBAGENT_MAX_DEPTH`), the scope
is declarative (`ADMISSIBLE_TOOLS`, with `web` riding every delegate by
default), the owner's approver is forwarded with the call renamed
`subagent → <tool>`, and every completion lands one `delegation` row.
The dependency graph replaces wave-orchestration: nodes start when
their prerequisites' artifacts verify, not when a sibling's report
arrives; `score(n) = Σ (cost(d) + score(d))` over unfinished
dependencies, derived on every read, zero only when every dependency is
verified; the resource edge is mandatory (two nodes naming one admitted
path never run concurrently); `settle()` runs the fact-gate predicate
over every non-verified node, failed ones included (`graph.rs`).

The calibration stream is the audit spine: ten ops today — `route`,
`tool_screen`, `turn`, `recall_hit`, `consolidate`, `propose`,
`eval_corpus`, `explain`, `route_judged`, `delegation` (`calib.rs:590`)
— through a bounded non-blocking queue (1024) drained by one
`fleet-calib` thread, one `write_all` per row under `O_APPEND`, a
2-second drain budget at teardown with undrained rows counted rather
than lost. An eleventh row shape, `delegation_judged`, is landed by the
delegate beat through its own append beside the stream. Rows are
redacted by design — task text never rides; joins are hashes.

`fleet judge` and `fleet delegate` close the two loops over sys1: the
judge sees the redacted route rows (workload, verdict, attempts,
outcomes — never the task text) and lands `route_judged`; the delegate
beat replays the child's own log and grades facts-gate-reports-
corroborate, landing `delegation_judged` keyed by the child's session.
`fleet explain` is eval-only and batch-only by construction: no verdict
reads the `explain` op, a socket-guard test greps the synchronous
modules for any reference to it, a drifted artifact is a named refusal,
and the prose lands hash-verified at `<home>/explanations/`.

The eval corpus is 20 fixed scenarios across 11 families, driven
headless against the mock server (never the routed client), graded
pass/fail per scenario with the first failing check named, aggregated
as passed/total, and landed as one `eval_corpus` row keyed to the
corpus's identity hash. `fleet improve` files proposals; only the
owner's `fleet improve apply` runs one through the local gate —
fmt, clippy, build, test (all four, even past a failure), plus the
corpus subprocess probe for source edits, which fails closed unless the
executable resolves under the gate root — and a green gate commits with
explicit paths while anything else reverts (git for repo-side, the
pre-image sidecar for home-side) and refuses by name.

## The surfaces

The TUI is a pure state machine (`app.rs`) rendered by `ui.rs` over a
crossterm loop (`mod.rs`); the agent runs on its own thread and
runtime, and the two meet at four channels — `UiEvent`, `Command`,
`ApprovalRequest`, `StatusUpdate`. Eight modes (Chat, Sessions,
Approval, Lanes, Explain, Settings, SettingsEdit), a board pane cycling
the three read-only boards (Fleet's own routing state, second-brain's
derived state files, git facts per project) under a snapshot contract —
a refused read keeps the last good snapshot visible and names why. The
settings pane (`Ctrl+,`) lists the ten scalar knobs as cards and edits
in place through the one writer the CLI shares, seeding the editor from
the resolved value (empty when the environment owns it).

`fleet settings set` reaches the list-shaped surfaces the pane cannot
(see Findings): `provider.add:` / `provider.remove:` /
`workload.set:` / `workload.remove:`, with the destructive rule —
removing an override of a compiled-in provider reverts it, removing one
the file added removes the provider from every walk and is refused
without `force`.

## Invariants (verified in code, not just in docs)

- **Model-visible ⟺ logged**: the log reconstructs every request; the
  system prompt, the compaction instruction, and the tool declarations
  are compiled-in constants, never logged; dynamic seams (skills,
  memory, lane joins) each get their own record type.
- **Zero real network in tests**: the integration suite spawns
  `mock-server` cross-process; lane paths drive `mock-mcp` or the real
  sem1 lane; the one live-API test is `#[ignore]`d and self-skips
  without a key.
- **Credentials never print**; doctor masks to the last four
  characters; key NAMES appear in docs, values never.
- **A lane child never inherits the environment**: `env_clear()` plus a
  named minimal base; `DEEPSEEK_API_KEY` is on no lane's list.
- **The gate is local** (CI is disarmed by budget): fmt, clippy, build,
  test — with rustfmt and clippy absent on this machine, so style is
  matched by hand and the absence is disclosed in every recap.

## Findings

Classified per the deep-dive discipline: a confirmed defect is proved
against the code; an assumed gap states the assumption and waits for
the owner; enhancements are offers, not plans.

### Confirmed

1. **The TUI settings pane cannot reach the list-shaped surfaces.**
   `commit_setting` carries four prefixed branches (`provider.add:`,
   `provider.remove:`, `workload.set:`, `workload.remove:` —
   `tui/app.rs:701-716`), but the editor is only ever seeded from
   `settings::states`, which maps the ten-entry `SETTINGS` table
   (`settings.rs:395-433`), so no pane-reachable key takes those
   branches. The settings-surface plan's inventory promised roster
   candidates and routing preferences in the pane (plan C1,
   `docs/plans/2026-10-15-settings-surface.md:26-31`); the plan is
   marked complete and the recap discloses only C4's in-pane
   confirmation gap. The list surfaces work — from the CLI. The pane
   half is unbuilt and was not disclosed as such.
2. **Doc drift, four instances, behavior verified against the
   constants**: `calib.rs`'s header says "six ops" above a ten-op `OPS`
   array; `calib.rs`'s consolidate prose names three actions over a
   four-word `ACTIONS`; `eval.rs`'s probe docs say "ten deterministic
   runs" against a 20-scenario corpus; `services/README.md` says "the
   four fleet lane cores" while five lanes (blend1 added) resolve in
   `fleet doctor`. `docs/architecture/overview.md` is the largest
   instance — a slice-1 snapshot missing 30 of 45 modules.
3. **`delegation_skips` has no live consumer**: the routing ride-back
   (`CalibrationCell`) is fully wired into `route.rs`; the delegation
   beat's parallel cell is exercised only by the eval corpus's
   `delegation-loop-closes` scenario and the `fleet calib --delegation`
   surface. The two cell implementations also disagree on whether
   waived rows count toward the fit sample (`delegate.rs:1783` includes
   them, `calib.rs:1956` excludes them) — one of the two is wrong for
   the same question.

4. **`graph.rs` documented unlock as two conditions while
   `Unlock::is_unlocked` requires three booleans** (`deps_verified`
   beside the score). The assumption held: it was a doc lag, not a
   second reading of the code, and `Graph::unlock` and `Graph::ready`
   now say three. Closed with the GUI revamp's delegation increment,
   which had to render the conditions the code actually requires — so
   `graph::state_word` is public and the browser's panel names a node's
   state through the same function the terminal does, leaving one
   naming rather than two that can drift.

### Assumed gaps (stated, not planned)

- **KI-068's timing gap** (recall bumps fire before the model call, so
  a failed run still bumps every surfaced fact) is open with slice-13's
  diagnosis work named as the owner. Assumed intentional sequencing;
  the fix would move the bump after the first successful response.
- **The `recall_hit` row for session recall** (the archive plan's C7)
  remains deferred by the module's own record; assumed deliberately
  later, since routing a synthetic fact through the corpus bump would
  rewrite a session log.

### Enhancements (offers)

- The settings pane's list surfaces: the writer, the destructive rule,
  and the CLI branches all exist; the pane needs a list-rendering card
  and an editor that seeds from a picked entry — the smallest honest
  close of finding 1.
- A `web`-leg line in `fleet doctor` (the archive plan's deferred C6):
  blend1's own doctor report already carries the availability JSON; the
  check is a read of what the lane already answers.
