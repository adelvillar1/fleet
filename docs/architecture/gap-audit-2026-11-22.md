# The gap audit — 2026-11-22

*(appended to the original deep-dive at its own request: the owner named this
the moment to reconcile what was identified against what never materialized.)*

The question was posed after the owner's verdict on v0.9.0's UI — *"most pages
look the same, no improved usability and information relevance"* — read against
the plan board and the deep-dive's own findings. The answer splits two ways:
what never materialized because it was **drafted and never stood in a goal**,
and what never materialized because it was **identified in prose and never
became a plan at all**.

## 0. The process critique — the contract the owner named the same night

The owner's ruling after the relevance-pass verdict: *"most of the additional
requests were added towards the 'end' of the plan, so you are not following
the plan as a contract process."* Measured and accepted: eleven drafted plans,
plus this whole day's added requests (kanzo, the mini console, tuios, the
TUI panels, compression), entered the work as **appended threads** — not as
amended contract rows with ACs and sequence slots. The relevance pass is the
first request that entered a plan before its work started.

**The contract, henceforth the process for this repo:**

1. **A plan row on intake, or the request is not accepted.** Any request the
   owner makes, any audit finding, any named errand is amended into the plan
   doc it belongs to (ACs written the day it's made) or into a new plan doc
   with `status: active` — never appended "at the end" of a conversation.
2. **Rows before threads.** The plan doc is the contract a writer implements
   against; the conversation is where rows are born, not where they live.
3. **A slot or a named gap.** A plan without a standing-goal slot is named in
   the next status report as a gap (this file), with an owner decision.
4. **Supersession is a written ruling, not a silent drop** — per row: landed
   in ⟨X⟩, or still real.
5. **Staged for CLAUDE.md** (the house rules file is agent-write-protected and
   the owner's consent is pending): the four numbered rules above, placed in
   CLAUDE.md before "Today's state", worded as this section words them,
   attributed to the owner's 2026-11-22 critique.

## 2. Identified in prose, never became a plan

- **The relevance principle itself.** The deep-dive's language had it
  early (design-system.md's *"a console that reads like a desk"* was already
  in the tree pre-face-rethought); the face plan carried it as an ambition;
  nothing made it the organizing rule of a page — until 2026-11-22's
  relevance pass. The owner's complaint ("no improved usability and
  information relevance") is this gap; the pass is its remedy.
- **The "assumptions to confirm" list never got ruled on as a whole.** F3.1–
  F3.4 and F6 were each silently settled by later work (cards.rs, the corpus
  resolver, the press primitive, test-support, CLAUDE.md deferring versions
  to `Cargo.toml`); F5 was drafted but never dispatched. They are now marked:
  the deep-dive's four *assumed* families are all **ruled: fixed** since;
  F5 (the split) remains the only one still open as its own question.
- **48 duplicate crate versions** (`base64` ×3, `getrandom` ×3, `hashbrown`
  ×3) — identified 11-20, drafted the same day, untouched since.

## 4. The closure order

1. The relevance pass lands (in flight) — it is the owner's verdict on the ship,
   and the drafts 1–6 dispatch AFTER it: `bridge-module-split` +
   `appjs-module-split` first (their preconditions are all met and nothing
