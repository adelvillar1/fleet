# Plan: the U-reskin — the production faces under the U-ledger

## Context

The UX trilogy is approved: three working reference mockups
(`docs/design/fleet-onboarding-mockup.html`, `fleet-workspace-mockup.html`,
`armada-workspace-mockup.html`) and the design-system ledger
[`UI-DECISIONS.md`](UI-DECISIONS.md) at **U0–U41** — the owner's words: *"the
design is approved"*, with the amendments recorded (pinned composer U20, the
thread pane U39, Intelligence U40, the system-one step U41). The production
faces still render the old system. This plan implements the ledger across the
real surfaces: the browser face (`src/gui/assets/`), the TUI, the CLI verbs and
`fleet onboard` — with fleet-desktop inheriting the face automatically (U29:
no second frontend, no second transport). Every phase cites the `U` ids it
implements and ships at the visual bar (hard rule 11), verified against the
mockups side by side.

## Design choices inherited (the ledger)

Conforms to **U0–U41** — in particular U4 (the nine-signal palette law, no
tenth hue), U5 (tokens as custom properties, both themes, zero hardcoded
literals), U9 (the shell grid), U29 (armada additive), U30–U33 (desk loop,
calibration word, memory dream, learning), U34–U38 (setup as graph growth),
U39 (the thread pane), U40 (Intelligence), U41 (at minimum one system-one
model). And **D0–D6**, hard rule 5 (reconstructable from the log), hard rule 11.

## Decision-model check

No sys1 head fits: theming, layout, and rendering are deterministic plumbing;
quality is graded by the face harness, the four-leg gate, and the visual check
against the mockups — never by a per-item judgment.

## Approach — six cuts, each atomic

One design token set first (nothing else can theme without it), then one
surface group per cut, the harness green at every step. Each cut is its own
release (the house rule: a user-facing change bumps the third segment).

1. **Cut 1 — tokens + shell (0.7.1, U4–U11).** `app.css` gains the token set:
   the nine signals + translucent washes, ink/panel/raise surfaces, line/line2
   translucent borders, three radii, one shadow, the three type voices, and
   the motion contract (one ambient layer, prefers-reduced-motion honored,
   a Motion switch). Theme: night default, Day Watch via `[data-theme]`, a
   chrome toggle. The shell: rail reorganized to Mission / Surfaces (live
   counts) / Saved views / tissue explainer; the lens-head pattern (title +
   sub + tools). Existing sections keep working — tokens are additive and
   components migrate section by section.
2. **Cut 2 — Intelligence (0.7.2, U40).** The Memory surface becomes
   **Intelligence** with four segments: Memories (basis ladder, anti-vectors,
   Dream — `/api/memory` + consolidation as today), **Skills** (`/api/skills`
   exists; render active/proposal states, the gate-apply action),
   **Tools** (new read: the bounded surface with builtin/lane/MCP kinds and
   read/write/destructive classes), **Workflows** (new read: chains as a stage
   track, runs graded). The tissue graph carries the intelligence family in
   teal (hue = family, icon+label = kind).
3. **Cut 3 — Threads (0.7.3, U20/U39).** The composer pinned to the bottom of
   the chat area; the transcript auto-follows only while already at the end;
   the collapsible **thread pane** listing the objects the conversation
   generated (deliverables, facts written, grades, lessons), color-dotted,
   fresh rows pulsing, click = pivot.
4. **Cut 4 — Desk + Calibration (0.7.4, U30/U31).** Deliverable cards render
   the five-stage pipeline with the current stage lit, coverage, and named
   refusals **on the card**; advance/settle wired to the existing desk
   endpoints. The calibration surface: confidence meters, graded outcomes, and
   the owner's agree-or-disagree riding the same append-only row.
5. **Cut 5 — Onboarding + setup (0.7.5, U34–U38/U41).** The setup lens on a
   fresh home — setup as graph growth, wired to the real `/api/onboard` flow:
   the install node, the account, **the judgment model step (U41: at minimum
   one system-one model; Fastino/Liquid/Drex linked to their own pages —
   Liquid is d1, never jev)**, the proof, the folder grant, and armada
   provisioning as the same gesture. Empty states name the step that fills
   them; skipped steps stay named.
6. **Cut 6 — TUI + fleet-desktop (0.7.6, U1/U15/U16/U29).** The TUI boards
   adopt the status color law and the palette pairs (the armada board is
   already visual — this is the color contract, not a rebuild); fleet-desktop
   verified wrapping the reskinned face over the same server.

## Files to be touched

**Face:** `src/gui/assets/app.css` (tokens), `app.js` + `index.html`
(sections, ROUTES/GROUPS/PANEL_EL), `src/gui/server.rs` (the new reads:
tools, workflows, intelligence aggregate), `src/gui/bridge.rs` (the reads
over the existing registries), `tests/face/harness.mjs` (branches + cases +
the rail-count pin). **TUI:** `src/tui/ui/*.rs`, `src/boards.rs` (styles only).
**Onboard:** the `/api/onboard` flow + the setup lens. **CLI:** none new.

## Out of scope

- Lane 2 (the org); any new agent capability (the reskin renders what exists).
- The vault UI; a mobile app; rewriting app.js wholesale (conventions stay).

## Verification

Per cut: `node tests/face/harness.mjs` green (no case regressed, new cases for
new sections), the four-leg gate, and the visual check — the section side by
side with its mockup. The plan closes `completed` only with every criterion
ticked and the owner's beta bar untouched (beta is the owner's call).

## Risks

- **app.js is large and conventional** — the reskin is incremental per
  section, harness green between sections; never a big-bang rewrite.
- **Theme regression on untouched sections** — tokens are additive; a section
  only joins the system when it is migrated in its own phase.
- **The harness rail-count pin** — GROUPS changes move the destination count;
  the pin updates in the same change (KI-447's lesson: the note rides the
  state, not the DOM).

## Dependencies

- [`UI-DECISIONS.md`](UI-DECISIONS.md) (U0–U41, settled + approved) and the
  three mockups. No new backend capability beyond reads over existing stores.

## Notes

The cut order is the dependency order: tokens first (everything themes through
them), then the shell (everything lives in it), then the surfaces (each one
phase), then onboarding (it grows the same surfaces), then the TUI and the
shell wrap. The owner activated the plan 2026-11-12 ("let's get the re-skin
activated and implemented as designed").
