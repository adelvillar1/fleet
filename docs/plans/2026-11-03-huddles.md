# Plan: huddles — the room where you and your bots work

## Context

Fleet's bots have no surface in the main app. The bot face (`fleet bot`,
the phone PWA) is assistant-first and a second window; the console's
`bots` destination is channels and pairing, not conversation. Yet the
session machinery already carries the shape of an inter-persona
conversation — `Start.personas` (join order, first = lead), a standing
`goal`, `Join`/`Leave` records, and `Assistant.persona` bylines — because
the bot face built it. What it does not do is let anyone but the lead
speak: the loop reads the lead once and only that role's overlay rides
the run (`agent.rs`, `bridge.rs`), so a persona added with `+` is logged
and then inert.

The owner's ruling: bring this into the console as a **huddle** — a
Slack-shaped room where the owner and one or more bots exchange
messages, address each other with `@`, post deliverables in-line, and
break out into child huddles. The rulings that shape it: every member
sees every message; a bot speaks with its own tools, skills and voice; a
bot may address another member, or **recommend convening one when the
brief exceeds the huddle's capabilities**; deliverables post in-line;
destructiveness is judged by sys1 rather than a static class; the
composer keeps ask / autonomous / full access; a bot's name and optional
avatar are the owner's; the owner's SOUL is the guardrail every bot
speaks within.

## Precedents this plan answers

- **`docs/features/bot-app.md`'s six rulings.** #1 *assistant-centric,
  not work-centric* — that ruling orients the **bot face**: its unit is
  the persona, its inbox groups conversations by persona, and no session
  list appears. The huddle does not reverse it. It gives the **console's
  work face** a room whose unit is a session-with-members — the
  console's own idiom, the one Sessions already uses — while the bot
  face stays the assistant-first window over the same bridge
  (2026-10-28). #3
  *a persona is a contract, not a mascot; no portraits* — revised by the
  owner below: an **optional, owner-supplied** image, shown in rows and
  member stacks and never beside a message; absent one, the derived
  initial stands. #4 *inter-persona conversations* — this plan
  implements them in the console. #5 *only destructive acts take the
  seat* — retained, and strengthened: sys1 judges what is destructive.
- **The settings-ux and plugins-ux shapes**: the page opens on the
  answer, the machinery sits behind doors that name themselves, one
  section at a time, a chained setting completes on one surface.
- **Hard rule 12 (self-containment)**: the huddle rides the one bridge
  the face already serves; nothing leans on the bot face's port, a
  checkout, or a foreign runtime.
- **The owner's mockups-first ruling** (plugins-ux): the screens are
  drawn and read before any code.
- **The identity slot** (`<home>/SOUL.md`, `home.rs`): the SOUL already
  overrides the system prompt and rides every run; this plan names its
  semantics — the guardrail under every bot's voice.
- **The approval gate's three modes** (`approvals.rs`): the huddle's
  composer inherits ask / yes / yes-guarded unchanged.

## Research

**What already exists** (the reuse inventory):

| seam | where |
|---|---|
| personas, goal, join/leave | `src/session.rs` (`Record::Start.personas`, `Goal`, `Join`, `Leave`) |
| assistant bylines | `Record::Assistant.persona` (`agent.rs`) |
| the lead's voice rides the run | `role_overlay` resolved in `bridge.rs`, appended in `composed_prompt` |
| roles as contracts | `Role { description, tools, skills, shapes, overlay }` (`roles.rs`) |
| a scoped child run | delegation resolves a role before spawn and narrows the declaration (`subagents.rs`) |
| sessions with personas | `Bridge::new_session_with`, `join`, `leave`, `inbox` |
| deliverable cards | the `send_file` tool and its artifact row in the transcript |
| the right pane | `files · code · preview · explore`, and `#/file/<path>` opening the preview |
| the rail's grammar | `GROUPS` in `app.js` (work / intelligence / knowledge / system) |

**The gaps:**

- **G1 — multi-persona is a label.** Only the lead authors turns; a
  persona added with `+` never speaks, brings no tools, no skills, no
  voice.
- **G2 — no mention directive.** Nothing lets a member address another;
  `@name` in prose has no meaning.
- **G3 — no per-speaker scope.** Tools and skills are the session's, not
  the speaker's, so bots differ only in overlay text.
- **G4 — no capability-gap recommendation.** A huddle cannot notice it
  lacks the role a brief needs, and cannot propose convening one.
- **G5 — no huddle surface.** No rail entry, no room, no member stack,
   no states, no in-line deliverable tie.
- **G6 — destructiveness is a static class.** The gate holds a fixed
  always-ask list; the owner's ruling is that sys1 judges it.
- **G7 — identity is derived-only.** A role's mark is its first initial;
  an owner who wants a bot named `bob` with a face has nowhere to put
  it, and the SOUL's guardrail semantics are unnamed.

## Approach

**A huddle is a session type, not a second agent.** The session already
carries the members, the goal, the bylines and the overlay seam; the
loop already composes a guardrail base and a voice on top. This plan
adds three model seams — the mention that switches the speaker, the
scope that follows the speaker, the recommendation that grows the
membership — and one surface that renders the room, plus the two
identity rulings. Each phase is independently shippable; the mockups
come first, as the owner ruled.

Phases:

0. **Mockups** — four screens drawn and read (C1).
1. **The model** — a huddle is a session; mentions route; scope follows
   the speaker; a recommendation grows the membership (C2–C5).
2. **The surface** — the rail, the room, the in-line deliverables, the
   states (C6–C8).
3. **Breakouts** — a huddle spawns child huddles (C9).
4. **sys1 judges destructiveness** (C10).
5. **Identity** — the optional avatar and the SOUL's guardrail (C11,
   C12).
6. **Verification** — the harness pins and a live end-to-end huddle
   (C13, C14).

**Decision-model check:** the plan carries one per-item judgment and it
is the owner's own — **sys1 judges whether an action is destructive**,
with the verdict riding the seat as data (accuracy and accountability
pay; the lane call is spent once per held action, and the fallback keeps
the gate alive when the lane is down). The capability-gap recommendation
and the skill selection are *not* sys1 jobs: the recommendation is the
speaking model's own proposal over the role roster, and the skill
ranking rides the existing router/ranker machinery.

## Use cases

- [ ] A: the owner opens the huddles rail and sees every huddle in one
      glance — active, inactive, ended — with who is in each and what
      each produced.
- [ ] B: the owner opens a huddle and reads the room: the goal, who is
      here and their voices, the transcript with bylines, and the
      deliverables posted in-line.
- [ ] C: the owner posts `@scholar` and the scholar answers in its own
      voice with its own skills.
- [ ] D: a bot addresses another bot with `@`, and the two exchange a
      review request without the owner relaying it.
- [ ] E: a bot recommends convening a role the huddle lacks, and the
      owner presses one convene to add it.
- [ ] F: the owner posts a deliverable and opens it in the right pane
      without leaving the huddle.
- [ ] G: the owner breaks a phase out into a child huddle and finds it
      from the parent.
- [ ] H: the owner ends a huddle and finds it under ended with its
      deliverables intact.
- [ ] I: the owner renames a bot and gives it a face; the mark appears
      in the rows but never beside a message.

## Acceptance criteria

- [ ] **C1 — the four screens are drawn.** Static HTML mockups at
      `docs/plans/mockups/2026-11-03-huddles/` render the huddle rail,
      the open huddle, the seat with sys1's verdict, and the breakout
      tree at 1440×900 with no horizontal overflow or clipped text, every
      row and primary action at least 44 px tall, and each persona mark's
      ink clearing AA on its disc.
- [ ] **C2 — a huddle is one session with members.** Creating a huddle
      with a goal and one or more bots writes a `Start` record whose
      persona set is the join order and stores the goal; the huddle
      document and rail read both back, and a session created without
      personas is not a huddle.
- [ ] **C3 — a mention routes the turn to the named member.** Posting
      `@name` writes a `Mention` record (member + kind: directive | ask |
      review); the next assistant turn is authored by that member — the
      `Assistant` record's `persona` names it and that member's role
      overlay rides the prompt; `@you` raises a needs-you on the row and
      starts no run. A name that resolves neither as a member nor as a
      role this home keeps is refused by name; a role the home keeps
      becomes a recommendation (C5), not a silent no-op.
- [ ] **C4 — a bot speaks with its own scope.** The speaking member's
      turn carries its role's tools: a role that names tools admits
      exactly those, and the declaration snapshot follows the switch so
      the log stays the prompt's truth. Each member's assigned skills
      lead the run's declaration, so the prompt's cap never pushes a
      member's own skill out of sight; the library itself is unchanged
      and every speaker may load any declared skill. A role that names
      nothing leaves the huddle's own standing, and a role that does not
      resolve leaves the turn unnamed rather than failing it.
      *(Amended on implementation: per-turn skill narrowing would mean a
      second skills declaration per run, and the `skills` record is the
      usage-rate denominator; leading the list gets the same reach
      without touching it. Skills ranked for the problem shape are out —
      that is the ranking machinery's own increment.)*
- [ ] **C5 — a bot can recommend a member the brief needs.** When the
      huddle's capabilities do not cover the brief, the speaking bot can
      address a role the home keeps beside the room — `@role <why>` —
      and the proposal lands as a `Recommend` record (role, reason,
      author) and one suggestion card with a single convene press; the
      address does not move the speaker, and nothing joins on the model's
      say-so. *(Amended on implementation: the recommendation rides the
      same `@` idiom rather than a typed tool, so the room has one way to
      address a person or a role.)*
- [ ] **C6 — deliverables post in-line.** A `send_file` inside a huddle
      renders an artifact card in the transcript at the post's position,
      and the card's press opens the file in the right pane's preview
      tab.
- [ ] **C7 — the huddle rail carries the three states.** `#/huddles` in
      the work group lists huddles in active / inactive / ended
      sections, each row with its member marks, its state word, and its
      deliverable count; the states derive from the log and the live
      window, and a huddle ends only by the owner's act.
- [ ] **C8 — the open huddle reads as a room.** The head carries the
      name, the goal, the member stack with each bot's voice line, the
      state chip, and the composer mode chips; the transcript renders
      bylines, @mentions, and review requests in order; the composer
      offers an @ picker over the huddle's members and the
      ask / autonomous / full-access modes.
- [ ] **C9 — a breakout is a child huddle.** A huddle can spawn a child
      huddle carrying the parent's goal and a phase brief; the parent's
      head lists its children with their states, and a child opens from
      the parent.
- [ ] **C10 — sys1 judges destructiveness.** An action the gate holds
      carries a `destructive` verdict judged by sys1 with its reason,
      rendered on the seat as data beside the approval controls; when
      sys1 cannot answer, the gate falls back to the standing destructive
      class and names the degradation on the seat.
- [ ] **C11 — an optional avatar, a free name.** A role may carry an
      owner-supplied image; it renders in the rail row, the member
      stack, and the persona card, and never beside a message; absent an
      image the derived serif initial stands, and renaming a bot is
      renaming its role file.
- [ ] **C12 — the SOUL is the guardrail.** The shipped default names
      the four virtues — truthful, honest, respectful, solution-oriented;
      the composition keeps the SOUL as the prompt's foundation and the
      role overlay inside it, closed by a standing constraint that the
      guardrails outrank the voice.
- [ ] **C13 — the gate.** fmt, clippy `-D warnings`, release build, and
      tests exit 0; the face harness pins the huddle cases (create,
      mention, scope, recommend, deliverable, breakout, end) and the
      sys1 seat case.
- [ ] **C14 — live proof.** On a scratch home: a huddle created, a bot
      convened, a mention routing a turn, a recommendation convening a
      second bot, a deliverable posted in-line and opened in the pane, a
      breakout spawned, and the huddle ended — each step observed in the
      live face.

## Out of scope

- **Retiring or converging the bot face.** It stays the assistant-first
  second window over the same bridge (the 2026-10-28 ruling).
- **Threads, reactions, presence, typing dots** — the Slack surface
  beyond the room, the mention, and the deliverable.
- **Auto-convening on a recommendation.** The bot recommends; the owner
  presses convene. Auto-convening is a later ruling, not this plan.
- **A general rewrite of the approval gate.** Only the destructive class
  becomes judged; the modes and the seat's shape stand.
- **Voice, video, or external invites.**
- **Avatar art direction.** An owner-supplied image is stored and
  rendered; nothing generates a face.

## Risks

- **The speaker switch touches the core loop.** The single-persona path
  must stay byte-identical when no mention occurs; the existing lead-only
  tests pin it, and the switch is a re-read of the lead after a mention,
  not a second loop.
- **A role-scoped tool set could strand a bot.** A bot whose role admits
  a tool the task does not need is fine; a bot whose role *excludes* a
  tool the task does need fails mid-turn. The recommendation (C5) is the
  answer, and the scope's named refusals are the evidence.
- **sys1 judging destructiveness spends a lane call per held action and
  adds latency.** Mitigation: the verdict rides the seat as data and is
  calibration-recorded; the lane-down fallback keeps the gate alive and
  names itself.
- **The SOUL replaces the system prompt, so a short custom SOUL drops
  the harness brief.** The shipped default must carry the full prompt
  plus the four virtues, and the closing constraint must survive a
  custom SOUL.
- **Scope.** Fourteen criteria across six phases. Mitigation: each phase
  ships alone; the mockups gate the surface's shape before any code.

## Notes

- The owner's Slack analogy is the design's spine: a room, members who
  see everything, `@` as the directive, files posted in-line, and a pane
  for looking closer.
- Alternatives considered: a separate huddle agent loop (rejected — the
  session, bylines, overlay and delegation already carry it; a second
  loop would fork hard rule 5's log contract); auto-running a mention
  without a budget (rejected for now — the huddle's turn budget bounds
  it, and `@you` never runs); convening a recommended bot automatically
  (rejected — recommend means the owner presses).
