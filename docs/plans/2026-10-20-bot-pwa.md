# Plan: fleet bot — the assistant-first PWA on the remote face

## Context

The owner's decision (2026-10-20): a fleet bot GUI **separate from the
console**, reachable over the Tailscale setup that already exists, with the
**same backend**. A PWA is the delivery shape; the owner chose a
fleet-owned surface over Telegram, Buzz, and Matrix, installed from the
tailnet origin.

Most of the machinery is already in place:

- `fleet gui` runs **one process, one `Arc<Bridge>`, one agent thread**. The
  loopback listener and the remote listener share it (`src/gui/mod.rs`,
  `src/gui/bridge.rs`).
- The remote listener carries the trust model: paired devices, device
  cookies, a default-deny allowlist, the pairing page, and the relay
  (`src/remote/listener.rs`).
- The PWA layer exists: `build.rs` stamps every served asset with FNV-1a,
  the page asks for `?v=<stamp>`, the worker caches only those URLs, and
  manifest, worker and icons are served on both faces.
- The remote face installs over Tailscale HTTPS; the pairing card resolves
  a verified tailnet name.
- **The inbox read and the new-session route landed on 2026-10-26**
  (`7d2c81e`): `GET /api/inbox` on both faces over `Bridge::inbox` and
  `inbox_document`, with the bounded 16 KiB tail read, the seat-first order
  and the named refusals; `/api/session/new` and `/api/steer` admitted on
  the remote face.

What is missing is the **surface itself**, and — since 2026-10-28 — the
model underneath it.

## The owner's rulings

These are the contract's shape. Each was made out loud and is dated; a
later ruling supersedes earlier framing, never an earlier commit.

- **R1 · 2026-10-28 — assistant-centric, not work-centric.** The first
  mockup pass organized the inbox by work (sessions grouped by state, a
  workspace path in every row) and was rejected: *"this is just rehashing
  what fleet does, which is work centric; the whole bot idea is assistant
  centric."* The unit is a persona; the work is what it is doing for you.
- **R2 · 2026-10-28 — the roster.** Six personas, three of them domains
  rather than jobs: `scholar` (knowledge work), `presenter`
  (presentations), `advocate` (job hunting), beside `tower` (runs the
  work), `auditor` (checks what changed) and `clerk` (keeps the ledger).
- **R3 · 2026-10-28 — a persona is a skill list.** Each persona maps to
  the skills it loads from the canonical folder. The skills exist
  (`~/.agents/skills`, 453 of them); the mapping is a role file's
  `skills:` frontmatter, which `src/roles.rs` already reads.
- **R4 · 2026-10-28 — inter-persona conversations.** A conversation may
  hold more than one persona. It is held together by a **goal** — the
  owner's own words — which no join may change: *"non-destructive actions
  should be allowed as long as the original goal of the conversation is
  preserved."*
- **R5 · 2026-10-28 — the approval rule is binary.** *"Non-destructive
  should be allowed."* Reads, searches, appends and edits with a diff run
  without asking. **Destructive actions are held for the owner and flagged
  as destructive with a visual cue** — every time, with no always-allow.
- **R6 · 2026-10-28 — identity without portfolios.** Personas are
  recognizable (a derived mark, tinted), but a persona is a contract, not
  a character: no portraits, and the mark must be readable in every theme.

## Decisions

**D1 — one process, one bridge, one log. No second binary.** The bot app
is a second *shell* over the same `Arc<Bridge>`. A second process would
create a second agent thread and a second seat, and the seat's
single-answer guarantee would stop being true. The crate stays one static
binary.

**D2 — the remote listener's root is the bot shell; loopback keeps the
console.** Different origins, different installs, one backend: the console
is the desk cockpit, the bot app is the pocket surface.

**D3 — the bot app has its own PWA identity.** Its own manifest
(`fleet bot`), worker and icon; the console's desktop install and the bot
install coexist as two apps. The phone's existing install from the remote
origin updates in place on the next load, which is the intent.

**D4 — a separate client, not a fork of `app.js`.** The console client is
~14k lines; the bot shell targets ~900–1,300 lines against the same API,
using the console's tokens and primitives, not its component tree.

**D5 — the inbox is a projection, never a second state machine.**
`GET /api/inbox` maps the words `sessions_read` already derives
(`src/gui/bridge.rs`): `needs-approval` → `seat`, `working`/`active` →
`running`, the `capped`/`stopped` ends → `failed`, otherwise `finished`.
One derivation, shared with the console (KI-300's rule). Two additions
since the archive verb (`9f877f4`): `archived` gets **its own arm**
(presented through the filter, not silently folded into `finished`), and
`handed back` reads as an interactive conversation that stopped, which for
the phone is `finished`.

**D6 — a new conversation rides the route that exists.** `POST
/api/session/new` → `Bridge::new_session()` creates an ordinary log and
answers its id; the app then calls `/api/run?session=`. No alias route.
What changes with R1/R4: creation must carry the **persona** and the
**goal**.

**D7 — personas are the roles fleet already has.** A persona *is* a role:
`<home>/roles/<name>.md`, `Role { name, description, tools, skills,
shapes, overlay }`. The surface reads the catalog and never invents a
second identity system. `~/.fleet/roles/` is empty today, so the first
increment authors the six.

**D8 — the goal is the invariant.** A conversation's goal is written from
the owner's first instruction, shown as chrome (never inside the scroll),
and **never rewritten by a join**. A join is a **record in the log**
(*auditor joined · checks what changed*), because anything the model saw
must be reconstructable. A new goal is a new conversation, or an explicit
owner-authored goal-change event — not a side effect.

**D9 — only destructive acts take the seat.** Two classes.
**Non-destructive** — reads, searches, appends, edits that carry a diff —
run and are logged. **Destructive** — deletes, overwrites that discard
content, sends that cannot be recalled, force operations — are held every
time and carry a visual cue (red hairline, a `destructive` badge with the
warning glyph, the material that will be lost, a filled red action) and
**offer no always-allow**: a standing permission for an irreversible act
is a footgun. This maps to the approvals gate's existing always-ask class
(`src/approvals.rs`).

**D10 — identity is derived, never an asset.** A persona's mark is its
serif initial on an **opaque** disc (12% of a palette hue mixed with the
theme's surface), with a per-theme ink chosen to clear AA on that disc;
hues come from the console's lane palette. It works for one role or forty,
needs no art, and keeps the persona a contract rather than a mascot. No
portraits, no emoji.

**D11 — the mockup gate stands.** No GUI asset is written until the four
mockups are approved with a dated line in their `README.md`. They exist now
(2026-10-28) and await that line; B1 does not start before it.

**D12 — no push in v1.** The app pulls. Per-persona models, web push,
Telegram, voice, a workspace picker and multi-user accounts are out of
scope; the first is the next plan's "routing preference".

## The surface (what the mockups establish)

`docs/plans/mockups/2026-10-20-bot-pwa/` holds the contract's pictures:
`inbox.html`, `conversation.html`, `dispatch.html`, `install.html`, one
`mockup.css`, and a `README.md` carrying the research, the decisions, the
measured contrast table and the approval block.

**Inbox.** A rail of six personas with counts; the list grouped by
persona, each row led by its mark and what it said last; a compact strip
above holding **only what needs the owner** — which under R5 means
destructive acts and failures, never ordinary work. The workspace has left
the list; it appears once in the conversation. At ≥720 px the list gains a
detail pane beside it.

**Conversation.** The header carries the participant stack (overlapping
marks) and a `+`; the **goal** is chrome between the header and the
stream. Personas are bylined per turn; a join is its own row; the working
chip names who is working and carries Stop. Destructive acts raise the red
seat; nothing else interrupts.

**Dispatch.** Who takes it, then the brief, then the folder it runs in: the
persona is the first choice, because it decides tools, skills and recall.

**Install.** The tailnet-origin coach mark (iOS has no install API), the
standalone chrome, the icon pair with the maskable safe-area guide, and an
unreachable page served by the worker that says what is true.

## What the backend needs

None of this exists; all of it is small.

| fact | where it goes | why |
|---|---|---|
| `goal` on the session | `src/session.rs`, written from the owner's first instruction | the invariant R4 rests on; resume keeps it |
| `personas` on the session | `src/session.rs`, a set, first = lead | the inbox groups by persona and stacks marks |
| a join record | the JSONL log, `{type:"join", persona, at}` (and a leave) | model-visible ⟺ logged |
| a destructive class | `src/approvals.rs` and the tool declarations | R5's binary rule needs a per-action class |
| role files | `<home>/roles/{scholar,presenter,advocate,tower,auditor,clerk}.md` | R3's persona→skills mapping |
| the archived arm | `inbox_document`, `src/gui/bridge.rs` | `archived` currently falls through to `finished` |

Two follow: `sessions_read` rows must carry the persona (or the set) so the
inbox neither re-derives nor guesses, and `POST /api/session/new` must
accept `persona` and `goal` (both optional for back-compat, defaulting to
the leading role and the first message).

## Increments

Each increment is its criterion's deliverable. Landed work is recorded,
not re-planned.

**P1 — the role files (R3).** Author `scholar`, `presenter`, `advocate`,
`tower`, `auditor`, `clerk` under `<home>/roles/`, each with
`description`, `tools`, `skills` (names that **resolve in
`~/.agents/skills`**) and `shapes`, plus an overlay that states the voice.
`fleet roles` renders all six; a test asserts every named skill exists, so
a typo cannot ship silently.

**P2 — the session binding (R1, R4).** `Session` gains `goal` and
`personas`; creation accepts both; the log gains the join record; resume
and archive keep them. `sessions_read` exposes them per row.

**P3 — the destructive class (R5).** Add the class to the approvals gate:
a per-action `destructive` flag, the always-ask path for it, and no
always-allow for destructive actions. The flag rides to the face so the
cue is data, not a guess.

**P4 — the inbox revision (D5, and the archive drift).** Group by persona;
carry goal and participants in the row; give `archived` its own arm behind
the filter; `handed back` reads `finished` for a phone. Tests for a shared
conversation, an archived one, and a joined one.

**B0 — the mockups (gate).** Produced 2026-10-28; awaiting the owner's
dated line in the folder's `README.md`. **B1 does not start before it.**

**B1 — the shell split.** `bot.html`, `bot.css`, `bot.js`,
`bot.webmanifest`, `bot-sw.js`, the bot icon pair; a per-face asset set in
the routers; the remote allowlist adds the bot set and **removes**
`/app.css` and `/app.js`. The unpaired root stays the pairing page.

**B2 — landed (`7d2c81e`), revised by P4.** The read exists; the
projection's vocabulary follows P2/P3/P4.

**B3 — landed (`7d2c81e`), extended by P2.** The route exists; creation
carries persona and goal.

**B4 — the app.** The inbox from `/api/inbox` (persona rail, participant
stacks, the strip), the conversation (goal chrome, bylines per persona,
join rows, the destructive seat, the working chip with Stop), the dispatch
sheet (who takes it), and `/events` as the live channel with a 5 s
fallback poll.

**B5 — install and Tailscale verification.** The manifest type and
no-cache; the worker caches exactly `/bot.css?v=` and `/bot.js?v=`;
confirm install, standalone launch, and the offline retry page at the
tailnet origin.

**B6 — documents.** `docs/features/bot-app.md`; updates to
`remote-access.md`, `gui.md` (two shells, one bridge, personas, the
goal), `docs/architecture/surfaces.md`, and the `fleet help` line if it
describes the face.

## Acceptance criteria

**Personas and identity**

- C1 Every conversation names at least one persona; the inbox groups by
  persona; a shared conversation shows every participant's mark.
- C2 Each persona resolves to a role file whose `skills` all exist in
  `~/.agents/skills`; a test enforces the resolution.
- C3 Every persona mark's glyph clears **AA (4.5:1)** against its own disc
  in **paper, console and graphite**; the disc is opaque, so the ratio does
  not depend on the row behind it. (The mockups measure 5.2–9.3:1; the
  built app must be checked the same way.)

**The conversation**

- C4 A conversation's goal is written from the owner's words, shown as
  chrome, and unchanged by any join; resume keeps it.
- C5 A join writes a record in the log, and the transcript shows it; a
  replay reconstructs who participated and when.
- C6 A persona's admitted tools bound what it may do: a read-only persona
  cannot write, and the refusal is named.

**Approval**

- C7 A non-destructive action (read, search, append, edit with a diff)
  runs without a seat, and the run is logged.
- C8 A destructive action always raises the seat, on both faces; the card
  carries the destructive flag, names what will be lost, offers no
  always-allow, and states the goal it preserves.
- C9 A second answer from either face is refused as already-answered.

**Surface**

- C10 One process, one bridge: both faces read the same logs and the same
  seat; no second agent thread exists.
- C11 An unpaired request to the remote root gets the pairing page; a
  paired request gets the bot shell; loopback still serves the console.
- C12 The remote allowlist admits the bot assets and the routes the app
  uses; `/api/access`, `/api/channels` writes, settings, vault and
  `/api/pair/window` answer 403 by name from a paired device.
- C13 The inbox names its bound (50), groups by persona, and renders the
  four states; a waiting destructive seat sorts first; a row whose tail
  cannot be read is refused by name, never blank.
- C14 A conversation started from the dispatch sheet — persona and goal
  written — appears in the bot inbox, the console's Sessions page and
  `fleet sessions`, with the same id and log.
- C15 The app installs from the tailnet origin as **fleet bot**, launches
  standalone at `/`, and shows its own retry page when unreachable.
- C16 The worker caches only the two versioned bot assets; HTML, `/api/`,
  `/events` and `/pair` are never cached.
- C17 The app renders at 430 and 900 px without horizontal scroll, with tap
  targets ≥44 px and fields ≥16 px; no visible row, chip or badge is a dead
  end (`data-act` audit).

**Close-out**

- C18 The four-step gate is green by exit code (`cargo fmt --all --check`,
  `cargo clippy --all-targets -- -D warnings`, `cargo build --release`,
  `cargo test`), with tests for the persona binding, the destructive class,
  the inbox projection, the allowlist and the asset stamp.

## Out of scope

Portraits or illustrated avatars (D10); per-persona model routing and spend
policy (the next plan's "routing preference"); web push and VAPID; Telegram
changes; Buzz; voice; a workspace picker; multi-user accounts; rewind/diff
in the bot app; editing a goal in place (a new conversation instead,
pending the open question below).

## Risks and open questions

- **The backfill.** Sessions written before P2 have no goal and no persona.
  They read as *unassigned* rather than being invented into a persona; say
  whether the console rail should filter them.
- **A goal you cannot edit** may be wrong for a long session. The plan
  assumes a new conversation, or an explicit owner-authored goal-change
  event recorded in the log — the second is not built and needs a ruling.
- **Classifying destructive is a judgement per action.** Overwrite, delete,
  send and force operations are named; whether a `bash` command is
  destructive cannot be answered statically, so the class is declared per
  tool and per argument shape, with a conservative default for commands
  that mutate.
- **Shared conversations in the list** are filed under the lead persona
  (the mockups' choice), so the counts still count conversations.
- **Multi-persona streams cost tokens**: two personas, two prompts, one
  log. The working chip names who is working so the cost is visible.
- **A role that names a missing skill** must refuse to load with a named
  error (C2).
- **The phone's existing install updates in place** from the console to the
  bot app; the console is then unreachable from the phone — say so in the
  release note.
