# Plan: fleet bot — a bot-first PWA on the remote face

## Context

The owner's decision (2026-10-20): a fleet bot GUI that is **separate
from the console**, reachable over the Tailscale setup that already
exists, with the **same backend**. A PWA is the delivery shape. After
comparing Telegram, Buzz, Matrix, and a fleet-owned surface, the owner
chose the fleet-owned surface, installed from the tailnet origin.

The pieces are already in the right places:

- `fleet gui` runs **one process, one `Arc<Bridge>`, one agent thread**.
  The loopback listener and the remote listener share it
  (`src/gui/mod.rs`, `src/gui/bridge.rs`).
- The remote listener already carries the trust model: paired devices,
  device cookies, a default-deny allowlist, the pairing page, and the
  relay (`src/remote/listener.rs:55`).
- The PWA layer already exists: `build.rs` stamps every served asset with
  FNV-1a, the page asks for `?v=<stamp>`, the worker caches only those
  URLs, and the manifest, worker, and icons are served on both faces
  (`docs/plans/2026-10-20-pwa-shell.md`).
- The remote face already installs over Tailscale HTTPS and the pairing
  card resolves a verified tailnet name (`docs/plans/2026-10-20-pairing-qr.md`).

What is missing is the **bot-first shell**. The remote face serves the
console — the same `index.html`, `app.css`, and `app.js` — so a phone
gets the cockpit's information architecture, not an inbox. The target
architecture named the missing surface: "the phone web app is bot-first
(sessions grouped by project, tap into chat)" (`fleet-lane-service-target-architecture`).
This plan builds that surface, and only that surface.

What the current code does not offer, and this plan adds:

- `GET /api/sessions` reads the **archive only** (`src/gui/bridge.rs:2749`):
  id, model, created, ended, kind, workspace, channel, compacted. It has
  no live attention state and no last line, so it cannot answer "what
  needs me" or "what did it say."
- A run needs an **existing** session. `POST /api/run?session=<id>` drives
  a known log; an empty session is the face's launch session. There is
  no "start a new conversation" route, so a bot app would put every
  dispatch into one long thread.
- The remote allowlist serves `/app.css` and `/app.js`
  (`src/remote/listener.rs:55`). The bot shell needs its own assets in
  that list and the console's removed.

## Decisions

**D1 — one process, one bridge, one log. No second binary.** The bot app
is a second *shell* over the same `Arc<Bridge>`. A second process would
create a second agent thread and a second seat, and the seat's
single-answer guarantee would stop being true. The crate stays one
static binary.

**D2 — the remote listener's root is the bot shell; loopback keeps the
console.** Different origins, different installs, one backend. The
console is the desk cockpit; the bot app is the pocket surface. The
remote listener stops serving `index.html`/`app.*` and serves the bot
set instead. This is the split the trust model already implies: loopback
is owner trust, a paired device is a device.

**D3 — the bot app has its own PWA identity.** Its own manifest (`name:
fleet bot`), its own worker, and its own icon variant derived from the
existing serif-`f` mark. Because PWA identity includes the origin, the
console's desktop install (`127.0.0.1:3080`) and the bot install
(`https://<tailnet>/`) coexist as two apps. The phone's existing install
from the remote origin updates **in place** to the bot app on the next
load; that is the intent, since the console was never the right phone
surface.

**D4 — a separate client, not a fork of `app.js`.** The console's client
is ~9,800 lines. The bot shell is a small app (target ~800–1,200 lines)
against the same API, using the console's design tokens and a handful of
its primitives, not its component tree. Duplication is bounded and
named here; extracting a shared kernel is a later decision only if the
two shells converge.

**D5 — the inbox is one bounded read.** `GET /api/inbox` merges the
archive with the bridge's live attached state and a bounded tail read
per session. It is the bot app's only polling read; the conversation
still rides `/events`.

**D6 — a new conversation is its own route.** `POST /api/new` creates an
ordinary session log and answers its id; the app then calls
`/api/run?session=<id>`. A new conversation's workspace is the face's
working directory in v1; a workspace picker is a later increment, not a
hidden behavior.

**D7 — no push in v1.** The app is pull. Telegram remains an optional
pager (out of scope here), and web push (VAPID + a sender) is a later
plan. Bot profiles — a named identity with a role, routing preference,
and tool scope — are the **next plan**; this one makes the surface they
will live on.

**D8 — mockups gate the GUI.** No GUI asset is written — not
`bot.html`, `bot.css`, `bot.js`, the manifest, the worker, or the icon,
and not a change to either router's shell — until the mockups below
exist, render at the widths the app is for, and are approved. The ASCII
wireframes in this plan are the brief, not the mockups; they are too
coarse to accept a surface against.

## The mockup gate

Before B1, produce static HTML mockups under
`docs/plans/mockups/2026-10-20-bot-pwa/`, one file per screen, openable
in a browser with no server and no data:

| File | Covers |
|---|---|
| `inbox.html` | empty, one row, all four states, the filter open, a long last line |
| `conversation.html` | a live stream, a seat card, a failed run, a stopped run |
| `dispatch.html` | the new-conversation box, empty and typed |
| `install.html` | the installed app's chrome and the unreachable page |

Each file renders at 430 px and 900 px; the folder's `README.md` names
the states each screen covers and the width table. The mockups use the
console's palette and type; they introduce no second design language.
Review is the owner's: the mockups are approved with a dated line in
that `README.md` **before** B1 starts, and the built surface is later
compared against them, not against this document.

**Backend increments may proceed during the review.** B2 (the inbox
read) and B3 (the new-session route) are API work with tests and no
visible surface; they are not gated. B1, B4, and B5 wait for the
approval.

## The app

The wireframes below are the brief's shape. The approved mockups are the
artifact every acceptance check compares against.

### Inbox

```text
┌──────────────────────────────────────────┐
│  fleet bot                          ● 2  │  ← needs you (seat + failed)
│                                          │
│  ┌────────────────────────────────────┐  │
│  │ needs you · 2          [all ▾]     │  │
│  │ ────────────────────────────────── │  │
│  │ ● tower        needs approval   2m │  │  ← tap: conversation + seat
│  │   "Approve the write to docs/…"    │  │
│  │ ● coder        running         14m │  │
│  │   "Running the gate on the fix…"   │  │
│  │ ○ fleet        finished         1h │  │
│  │   "The plan is drafted; three …"   │  │
│  └────────────────────────────────────┘  │
│                                          │
│  ┌────────────────────────────────────┐  │
│  │ [  what should it do?            ] │  │  ← starts a new conversation
│  └────────────────────────────────────┘  │
└──────────────────────────────────────────┘
```

Group by workspace (project) under the filter; the row shows the state,
the age, and one clamped line of the last assistant message. States, in
priority order: **seat** (an approval is waiting), **failed**,
**running**, **finished**. A seat row is the top of the list and its
tap lands on the seat, not the top of the transcript.

### Conversation

```text
┌──────────────────────────────────────────┐
│  ‹  tower                     running ·  │
│  ──────────────────────────────────────  │
│  you   run the gate and fix what breaks  │
│  tower  I'll read the ledger first…      │
│         ⚙ bash · cargo test    (live)    │
│  ┌────────────────────────────────────┐  │
│  │ approval needed                    │  │
│  │ write_file · docs/known-issues.md  │  │
│  │ [once] [always] [deny]             │  │
│  └────────────────────────────────────┘  │
│  [ steer or answer…                  ]   │
└──────────────────────────────────────────┘
```

The same stream, the same seat, the same single answer. Stop and steer
are available while a run is in flight. A plan-mode run renders as the
plan card the console already draws; a rewind/diff is out of v1.

### Install

The tailnet origin (`https://<machine>.<tailnet>.ts.net/`) opens the
paired app, offers Add to Home Screen, and launches standalone. The
worker answers an unreachable navigation with a themed retry page that
says **fleet bot**, not fleet.

## Increments

**B0 — the mockups.** The four static HTML files and their `README.md`
under `docs/plans/mockups/2026-10-20-bot-pwa/`, each rendered at 430 px
and 900 px, every state listed in the table above. Nothing in
`src/gui/assets/` changes in this increment. The owner's dated approval
line in the README closes it; B1 does not start before that line exists.

**B1 — the shell split.** Add `bot.html`, `bot.css`, `bot.js`,
`bot.webmanifest`, `bot-sw.js`, and the bot icon pair to
`src/gui/assets/`, all included by `build.rs`'s stamp. Give the routers a
per-face asset set: loopback keeps `index.html`/`app.*`/`sw.js`; the
remote listener serves `bot.html` at `/`, `bot.css` and `bot.js` (with
`?v=`), `bot.webmanifest`, `bot-sw.js`, and the bot icons. Tighten the
remote allowlist: add the bot assets, **remove** `/app.css` and
`/app.js`. The unpaired root stays the pairing page.

**B2 — the inbox read.** Add `Bridge::inbox()` and `GET /api/inbox`, on
both faces, remote-allowlisted. The document: `read_at`, the bound
(`sessions: 50`), and per row `id`, `workspace`, `created`, `ended`,
`channel`, `model`, `state` (`seat`/`running`/`failed`/`finished`),
`seat` summary when present, `last` (one clamped line), `at`. The live
overlay comes from the bridge's attached map; the last line comes from a
bounded tail read of each log (last 16 KiB, parsed backwards for the
newest assistant message or failure record). A row whose tail cannot be
read carries `refused` naming why, never a blank that looks finished.
Tests: a finished session, a running session, a seat, a failed run, and
a session whose log is truncated.

**B3 — new conversation.** Add `Bridge::new_session()` and
`POST /api/new`, answering `{"session": "<id>"}`. It creates an ordinary
log through `Session::create`, so the archive, the console's Sessions
page, and the bot inbox all see it. Remote-allowlisted; loopback too.

**B4 — the app.** `bot.js` builds the inbox from `/api/inbox` on load and
on every `/events` event that names a session (with a 5 s fallback
poll); tapping a row opens `/api/session` for the replay and
`/api/state` for the live view, then appends `/events`. The composer
posts `/api/run?session=`. The seat posts `/api/approve` with the same
`decision` vocabulary the console uses. Stop and steer post `/api/stop`
and `/api/steer`. The dispatch box calls `/api/new` then `/api/run`.
`bot.css` reuses the paper palette, the serif display face, the stamp
style, the card frame, and the seat's visual language; it adds no new
design vocabulary, only a simpler information architecture.

**B5 — install and Tailscale verification.** Serve the manifest with
`application/manifest+json` and `no-cache`; the worker caches exactly
`/bot.css?v=` and `/bot.js?v=` and bypasses `/api/`, `/events`, and
`/pair` by path, exactly as the console's worker does. Confirm the
tailnet origin installs, launches standalone, and renders the retry page
offline. If the owner runs `tailscale serve`, it points at the remote
listener; the pairing card's verified tailnet branch already names that
origin.

**B6 — documents.** Add `docs/features/bot-app.md`; update
`docs/features/remote-access.md` (the remote face is the bot app; the
console is loopback), `docs/features/gui.md` (two shells, one bridge),
and the `fleet help` line for `--remote` if it describes the face.

## Acceptance criteria

0. **The mockup gate closes first.** The four screens exist under
   `docs/plans/mockups/2026-10-20-bot-pwa/`, render at 430 px and
   900 px, and carry the owner's dated approval in the folder's
   `README.md` before any GUI asset exists in `src/gui/assets/`.
1. `fleet gui` remains one process with one bridge: both faces read the
   same session logs and the same seat; no second agent thread exists.
2. An unpaired request to the remote root gets the pairing page; a
   paired request gets the bot shell. The loopback root still serves the
   console, unchanged.
3. The remote allowlist admits the bot shell and its assets and the API
   routes the app uses; `/api/access`, `/api/channels` writes, settings,
   vault, and `/api/pair/window` answer 403 by name from a paired
   device.
4. The inbox names its bound, groups by workspace, and renders the four
   states; a waiting seat is the first row; the row's last line is the
   newest assistant message (or the failure), never a blank that reads
   as success.
5. Tapping a row opens the conversation; the live stream appends;
   the composer sends; a seat renders as a card and is answered once
   (a second answer from the console or the phone is refused as
   already-answered).
6. A new conversation created from the dispatch box appears in the bot
   inbox, the console's Sessions page, and `fleet sessions`, with the
   same id and log.
7. The app installs from the tailnet HTTPS origin as **fleet bot** with
   its own icon, launches standalone at `/`, and shows its own retry
   page when the face is unreachable.
8. The worker caches only the two versioned bot assets; HTML, `/api/`,
   `/events`, and `/pair` are never cached.
9. The app renders at 430 px and 900 px without horizontal scroll, with
   tap targets at least 44 px, and no visible row, tile, or badge is a
   dead end (`data-act` audit).
10. The four-step gate is green, with tests for the inbox read, the
    new-session route, the remote allowlist, and the asset stamp.

## Out of scope

Bot profiles and rosters (the next plan); per-bot models, roles, and
tool scopes; push notifications and web push; Telegram changes; Buzz;
voice; a workspace picker; multi-user accounts; rewind/diff in the bot
app; theme parity beyond the paper palette and `prefers-color-scheme`.

## Verification

- The mockups are reviewed and approved in their README before any GUI
  asset is written; the built surface is then rendered at the same
  widths and compared against them.
- Playwright against the remote origin with a paired cookie at 430 and
  900 px: inbox states, tap-to-conversation, seat answer, stop/steer,
  new conversation.
- Raw HTTP: the remote root's shell, the manifest type, the worker's
  cache contents (only the two versioned assets), the 403s by name.
- Offline reload: the bot retry page.
- Install: the tailnet origin offers Add to Home Screen and launches
  standalone.
- Cross-surface: a session created in the bot app opens in the console;
  a seat answered on the phone is refused at the console.
- The four-step gate: `cargo fmt --all --check`,
  `cargo clippy --all-targets -- -D warnings`, `cargo build --release`,
  `cargo test`.

## Risks and open questions

- **The phone's existing install updates in place** from the console to
  the bot app (same origin, same `id`). That is the intended split, but
  the console is then unreachable from the phone; say so in the release
  note.
- **Client duplication.** The bot shell is deliberately small; if it
  grows toward the console, extract a shared kernel rather than fork
  further.
- **The tail read's cost.** 50 rows × 16 KiB is bounded and named; if it
  proves slow on a full archive, lower the row cap and say so in the
  document.
- **The serial run loop.** The inbox can show several active sessions,
  but the bridge's command loop runs one task at a time. Triage is
  accurate; parallelism is not promised. Name it when a bot roster
  arrives.
- **A new conversation's workspace** is the face's cwd until the
  workspace increment lands; the row says which workspace it recorded.
