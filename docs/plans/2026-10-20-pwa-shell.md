# Plan: The face becomes installable — a PWA shell with a strict cache boundary

## Outcome (2026-10-20)

All six increments landed. The build stamp is `build.rs`'s FNV-1a over
the served assets; the page asks for `app.css?v=<stamp>` and
`app.js?v=<stamp>` and only those URLs are immutable. The manifest and
icons are rendered from the rail's mark, the worker caches exactly those
two URLs and never HTML, `/api/`, `/events`, or `/pair`, and a navigation
that cannot reach the face gets a themed 503 retry page. The browser
floor and a 15-second boot watchdog show one card instead of a blank tab.

Verified live in Chromium on `127.0.0.1`: the worker registers and
controls, the cache holds the two versioned assets and none of the
session paths, an offline reload shows the retry page, an unsupported UA
shows the update card, and an aborted `app.js` shows the watchdog card.
Raw HTTP checks pinned the headers, the manifest type, and the binary
icons. The remote listener serves the same install surface to a paired
device — and the test that added that assertion found KI-275, a
pre-existing defect where the remote root answered the pairing page
before it read the cookie, so a paired phone could never reach the shell
at `/`. It is fixed and pinned.

The four-step gate is green: 1277 library tests plus every integration
suite, fmt and clippy clean, release built.

## Context

Qwen Code's PR #11722 (merged) adds installability to its daemon-served
web shell: a manifest and icons, a production service worker, a retry
page when the daemon is unreachable, and an ES5 browser guard with one
themed startup error. It also carries an Android WebView shell, which
the PR itself calls a development spike.

Fleet's phone story is a browser face: `fleet gui --remote` serves the
same editorial console over the machine's address, and a paired device
holds a cookie. What it lacks is the "app" part — Add to Home Screen with
a real icon, a launch that survives a cached-stale reload, and a readable
page when the face is down instead of the browser's own error. This plan
borrows the PWA layer and the worker's cache discipline, and explicitly
does not borrow the Android shell.

Three fleet-specific facts decide the shape:

- **The remote face uses a cookie, not a bearer header.** Qwen's worker
  bypasses requests carrying `Authorization`. Fleet's worker must bypass
  by path — `/api/`, `/events`, `/pair` — and cache only the two asset
  paths it was written for. A header test would miss the cookie.
- **Fleet has no content-hashed assets.** The assets are `include_str!`
  and served at fixed paths with no cache headers at all today, so a
  browser can serve a stale `app.js` after an upgrade. A `build.rs` hash
  gives the two assets a content address (`?v=<hash>`) without a bundler
  or a new crate; only those URLs are immutable.
- **Service workers require a secure context.** `http://127.0.0.1:3080`
  qualifies; the phone over plain LAN `http://192.168.x.x` does not. The
  installable path is loopback and HTTPS (Tailscale serve). The relay's
  `/s/<sid>/` subpath is per-session and is not made installable.

The Android shell stays out: a Kotlin/Gradle tree and a second toolchain
for a crate whose contract is one static binary, while the PWA covers the
home-screen need on both iOS and Android.

## Approach

**P1 — content addresses and headers.** `build.rs` hashes
`index.html`, `app.css`, `app.js`, the manifest, the worker, and the two
icons with FNV-1a (std only) and exposes `FLEET_ASSET_HASH`. The page is
served with the two asset URLs versioned. Headers:

- `/` → `Cache-Control: no-cache` (the HTML revalidates);
- `/app.css?v=<hash>`, `/app.js?v=<hash>` → `public, max-age=31536000,
  immutable`; the unversioned path → `no-cache`;
- `/manifest.webmanifest` → `application/manifest+json`, `no-cache`;
- `/sw.js` → `no-cache`, `Service-Worker-Allowed: /`,
  `X-Content-Type-Options: nosniff`;
- icons → `public, max-age=86400`.

The remote listener serves the same page and headers, so the two faces
cannot disagree about a cache.

**P2 — the install surface.** `manifest.webmanifest` (name/short name
`fleet`, `start_url: "/"`, `scope: "/"`, standalone, paper background
`#f6f4ef` and theme color, 192 and 512 PNG icons, `purpose: "any"`) and
two icons: the serif **f** on the graphite console ground with one
signal-blue rule, legible at 16px. The macOS squircle and its `.icns`
are the same mark with transparent margins, kept in `assets/` for a
desktop launcher. The
head gains the manifest link, an `apple-touch-icon`, and a `theme-color`
meta the theme script updates per theme (paper, console, graphite,
contrast). Icons are served by a small binary-reply writer because
`Reply.body` is a `String`.

**P3 — the worker.** `sw.js`, a classic script whose cache name carries
the build hash (`fleet-shell-<hash>`). Install skips waiting; activate
deletes only `fleet-shell-*` caches other than the current and claims
clients. The fetch handler returns early for every non-GET, every
cross-origin request, every path under `/api/`, `/events`, and `/pair`,
and any request asking for `text/event-stream`. It intercepts exactly two
paths — `/app.css` and `/app.js` carrying the current `v` — cache-first,
caching only a `200` `basic` response. A navigation is network-first; on
failure it answers a 503 retry page (themed, with a retry link). HTML is
never cached: an unavailable face gets a retry page, not a stale session.

**P4 — registration, guard, and the boot watchdog.** `index.html`
registers `/sw.js` after `load`, only when `window.isSecureContext`,
`navigator.serviceWorker` exists, and the browser is supported. An ES5
guard checks the floor fleet's CSS actually needs (`color-mix` and
`100dvh`: Chrome/Edge 111+, Firefox 113+, Safari 16.2+). A 15-second
watchdog shows one themed fallback card if `app.js` never marks the shell
mounted, so a failed script is no longer a blank page. `app.js` sets
`data-fleet-mounted` when its first load resolves, and the unsupported
guard's message wins over the generic timeout.

**P5 — the remote face.** The listener serves the same index and the PWA
assets, adds them to `ALLOWED_GET`, and keeps them paired-only: the
pairing page references none of them, and an unpaired request still gets
the pairing page or a 401. The remote worker is the same file, with the
same path-based bypass, so the device cookie can never be cached.

**P6 — tests, docs, and the live check.** Server tests pin the versioned
URLs, the header rules, the manifest type, the worker's
`Service-Worker-Allowed`, and the icons. The remote tests pin the PWA
routes as reachable for a paired device while `/api/settings` stays 403.
A Playwright pass registers the worker on `127.0.0.1`, asserts the cache
holds only the two versioned assets, asserts `/api/state` and `/events`
are absent from it, and loads an offline navigation to see the retry
page. `docs/features/gui.md` and `remote-access.md` name the installable
paths and the secure-context limit.

## Acceptance Criteria

1. `cargo build` exposes a hash that changes when any served asset
   changes; `/` links `/app.css?v=<hash>` and `/app.js?v=<hash>` and the
   manifest.
2. The versioned CSS/JS answer `immutable`; the unversioned paths answer
   `no-cache`; the HTML answers `no-cache`; the worker answers `no-cache`
   with `Service-Worker-Allowed: /`; the manifest answers
   `application/manifest+json`.
3. The manifest parses, names 192 and 512 PNG icons, and both icons
   serve with `image/png` and the right dimensions; an
   `apple-touch-icon` is linked.
4. On `127.0.0.1` the worker registers after load, and its cache contains
   exactly the versioned `app.css` and `app.js`; a second load serves them
   from the cache.
5. `/api/state`, `/api/*`, `/events`, and `/pair` never appear in the
   worker cache, and a fetch for any of them is not intercepted.
6. With the network offline, a navigation answers the 503 retry page;
   the page is never served from the cache.
7. Activating a new worker deletes only obsolete `fleet-shell-*` caches.
8. The remote face serves the manifest, worker, and icons to a paired
   device; an unpaired request is still the pairing page or a 401; a
   paired device's `/api/settings` is still 403 by name.
9. An unsupported browser (or one lacking `color-mix`/`100dvh`) shows the
   themed update message; a supported browser sees no change; a shell
   whose script never mounts shows the watchdog card within 15 seconds.
10. The four-step gate is green, and the live Chromium check reports no
    console errors and no API/SSE entries in the cache.

## Out of scope

- The Android WebView shell, Gradle/Kotlin, and a second toolchain.
- PWA installability through the relay's per-session `/s/<sid>/` path.
- Offline application use or offline sessions: only the two static
  assets cache; every read and stream is network-only.
- Push notifications, background sync, sharing targets, and a profile or
  credential store beyond the existing device cookie.
- Content hashing anything beyond `app.css` and `app.js`; new assets are
  network-only by default.

## Verification

- The four-step gate: `fmt --check`, `clippy --all-targets -D warnings`,
  `build --release`, `test`.
- Header checks with `curl -I` (or the crash-safe request helper) on `/`,
  `/app.css`, `/app.css?v=<hash>`, `/sw.js`, `/manifest.webmanifest`, and
  an icon.
- Playwright at 390, 900, and 1600 on `127.0.0.1`: registration state,
  `caches.keys()` and `cache.match` for each path, an offline navigation
  (context `setOffline(true)` or a stopped server), and the manifest's
  parsed values.
- A paired-device remote run: the PWA assets answer 200, `/api/settings`
  answers 403, and an unpaired browser still gets the pairing page.
